### Ma trận chuyển đổi cuối cùng (bắt buộc enforce)

```
PENDING         → REVIEWING (nút Duyệt+đẩy) | REJECTED | CANCELLED
REVIEWING       → APPROVED (webhook/script/tạm-tay) | CANCELLED
APPROVED        → CONTRACT_SIGNED | CONTRACT_FAILED (webhook/script/tạm-tay)
CONTRACT_SIGNED → CANCELLED (tay) | stations:DEPLOYING (nút tay hoặc auto xx ngày)
CONTRACT_FAILED → CANCELLED (tay hoặc auto xx ngày)
REJECTED        → PENDING (resubmit, giữ nguyên luồng CTV)
CANCELLED       → terminal (mọi chuyển đi đều 400, kể cả admin; chỉ SUPER_ADMIN override khẩn cấp có log)
```

### Bước 3 — Webhook 1Office 2 chiều + script demo chung hàm

Khẳng định câu hỏi của bạn: **đúng** — 1Office đẩy "đã duyệt" sang, web cập nhật status rồi **trả kết quả đồng bộ lại cho 1Office** trong cùng response (để BPA đi tiếp theo Success path).

1. Endpoint mới `POST /api/webhooks/oneoffice/proposal-status` (public, auth secret per `api_configs.auth_config`, rate-limit riêng):
   - Request: `{ event_id (idempotency), event: APPROVED|SIGNED|SIGN_FAILED, contact_code/proposal_code, event_time, note }`.
   - Xử lý: resolve `contact_1office_code → proposal_ids` → gọi `proposalLifecycle.transition()` (`APPROVED→CONTRACT_SIGNED/CONTRACT_FAILED`, `REVIEWING→APPROVED`) với `source=webhook` → ghi `api_queue_logs (direction=inbound)` + `proposal_activity_logs` → notify.
   - Response ổn định cho BPA: `{ success: true, data: { proposal_ids, old_status, new_status, applied_at } }`; BPA cấu hình Success path `$.success = true`, map `data.new_status` cho bước sau (đúng 2 khối Response trong ảnh). **Không đổi shape sau khi 1Office đã cấu hình.**
   - 1 contact → nhiều proposal: trả `applied[]` + `ambiguous[]` để xử lý tay, không tự đoán.
2. Script demo `backend/scripts/simulate-1office-event.js {proposalId, event}` gọi **chung** `applyExternalEvent()` với webhook, `source=script` + `manual_override=1` cho nhánh `APPROVED→CONTRACT_*` tạm-tay. Sau này bật webhook thì script nghỉ hưu, logic không đổi.

### Bước 4 — Worker vòng đời + nút tay tạo trạm + retry/cảnh báo

1. `backend/src/workers/proposalLifecycleWorker.js` (copy pattern `personnelSyncWorker`: `tick` + `cronMatcher.matches(lifecycle_check_cron)` + `start()` gắn `app.js`):
   - Job A: `CONTRACT_FAILED` quá `contract_failed_to_cancel_days` → `transition(...→CANCELLED, source=system_auto)`.
   - Job B: `CONTRACT_SIGNED` quá `contract_signed_to_station_days` **và** `station_id IS NULL` → gọi `convertProposalToStation()` → set `station_id`, station `DEPLOYING`.
   - Idempotent: kiểm tra lại status + `station_id` trong transaction trước khi làm; chạy lại không tạo trùng.
2. Retry: mỗi job có `attempts`, tối đa `lifecycle_max_retries`; lỗi (tạo station fail, DB deadlock) → exponential backoff + ghi `api_queue_logs(status=failed, retry_count)`; **hết retry → giữ nguyên status, ghi activity log `action=auto_failed`, tạo notification + (nếu có) queue entry cho ADMIN/SUPER "kiểm tra thủ công"**. Không bao giờ tự bỏ qua hay tự CANCELLED khi job B lỗi.
