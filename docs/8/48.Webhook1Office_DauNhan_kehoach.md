## 1. Tổng quan

```
1Office (BPA HTTP node)  ──POST JSON──▶  Web  → đổi status theo ma trận → trả response
        ◀── { success, data } ──┘  (BPA rẽ nhánh Success theo $.success = true)
```

Web là **đầu nhận thuần túy** (không gọi ngược). Mọi yêu cầu mới đều đã chốt trong mục 2.

---

## 2. Nhật ký xác nhận (toàn bộ thông tin đã chốt với user)

1. Web hiện tại là đầu nhận, 1Office đẩy lên, web trả response về (đúng thiết kế 46-Bước 5).
2. Xác thực: dùng **Bearer Token** (chuẩn, khớp dropdown Authorization của BPA); web chấp nhận cả `Authorization: Bearer` **và** `x-webhook-secret` custom.
3. `X-1Office-Signature` là chữ ký mặc định của 1Office — bỏ qua cho tới khi có tài liệu verify (lúc đó cộng thêm thành lớp 2).
4. Timeout BPA đặt **10–15s** (endpoint ta <500ms).
5. Retry BPA đặt **2 lần** (kết hợp `event_id` chống trùng tuyệt đối).
6. Body **JSON** đúng 7 key; response mapping theo bảng mục 4.
7. Endpoint: dev `http://localhost:3000/api/webhooks/oneoffice/proposal-status`, prod `https://tmtegreen.io.vn/api/webhooks/oneoffice/proposal-status`.
8. Sinh **cặp Bearer Token staging/prod** — user đã duyệt (chưa sinh, làm ở Đợt 1).
9. Code Bearer + rotation — user đã duyệt (chưa code).
10. Thêm UI cấu hình webhook trong `/admin/api-configs` — user đồng ý thiết kế (chưa code).

---

## 3. Endpoint hiện có (46-Bước 5, giữ nguyên khung — cập nhật tên event)

- `POST /api/webhooks/oneoffice/proposal-status`, rate-limit riêng, secret header, event `APPROVED|CONTRACT_SIGNED|CONTRACT_FAILED|CANCELLED` (**trùng tên status đích để khỏi nhầm**; hiện code 46 dùng `SIGNED`/`SIGN_FAILED` — đổi sang tên mới khi làm Đợt 1).
- Resolve `proposal_code` (tracking_code) ưu tiên, fallback `contact_code`; idempotency `event_id`; log inbound trực tiếp (không qua worker); response đóng băng.

---

## 4. Bảng mapping chốt (đưa admin 1Office cấu hình node HTTP)

**Bảng A — Body gửi sang (JSON):**

| Key | Kiểu | Giá trị trong BPA | Bắt buộc |
|---|---|---|---|
| `event_id` | Ký tự | ID duy nhất mỗi lần bắn (mã công việc + timestamp) | Có |
| `event` | Ký tự | `APPROVED` / `CONTRACT_SIGNED` / `CONTRACT_FAILED` / `CANCELLED` | Có |
| `proposal_code` | Ký tự | Mã đề xuất (= `tracking_code` ta đã đẩy sang) | Có (*hoặc* `contact_code`) |
| `contact_code` | Ký tự | Mã contact 1Office (dự phòng) | 1 trong 2 |
| `note` | Văn bản | Ghi chú/lý do (vào log + thông báo) | Không |
| `event_time` | Ngày | Thời điểm bắn | Không |
| `actor` | Ký tự | Người duyệt/ký bên 1Office | Không |

Ánh xạ event → ma trận (tên event **trùng tên status đích**): `APPROVED` → `REVIEWING→APPROVED`; `CONTRACT_SIGNED` → `APPROVED→CONTRACT_SIGNED`; `CONTRACT_FAILED` → `APPROVED→CONTRACT_FAILED`; `CANCELLED` → `REVIEWING→CANCELLED` (đường ma trận có sẵn, `note` bắt buộc làm lý do hủy).

**Bảng B — Response (kiểu Json):** Đường dẫn thành công `success` = `true`; đường dẫn dữ liệu `data`; biến nhận về `new_status` (Ký tự → `{http.nX.new_status}`), `event_id` (Ký tự), `applied_at` (Ngày).

**Cấu hình BPA đề xuất**: Authorization Bearer Token (secret staging/prod) · Body JSON · Timeout 10–15s · Retry 2 lần.

## 7. Rủi ro & lưu ý

- Secret lộ = giả mạo event → xoay ngay + check log inbound bất thường; không commit secret vào repo/docs.
- BPA giữ "Không gửi lại": mọi failed đều phải có người đọc (notify) + phát lại tay bằng script.
- `event_id` phải duy nhất thật phía BPA (không dùng timestamp tròn giây cho 2 node song song).
- Đổi shape response sau Đợt 2 → version endpoint mới, không sửa cái cũ.
