## 3. Thiết kế

### 3.1. Cấu trúc `layout_config` mở rộng

`layout_config.sections[]` hiện có 1 loại phần tử (section thường). Bổ sung loại thứ 2: **tab-group**.

```jsonc
{
  "rows": [],
  "sections": [
    { "id": "s1", "title": "Thông tin khách hàng", "collapsible": false, "rows": [ /* ... */ ] },

    // ... các section thường khác ...

    {
      "id": "tai_chinh_nqlk",
      "type": "tabs",                                  // <-- loại mới
      "title": "Nhượng quyền và Liên kết",
      "visibleWhen": { "field": "mo_hinh_dau_tu", "value": "NQ_LK" },
      "tabs": [
        {
          "id": "nqlk_nq",
          "title": "Nhượng quyền",
          "sectionRefs": ["station_proposals_view_s6"]   // tham chiếu section có sẵn
        },
        {
          "id": "nqlk_lk",
          "title": "Liên kết",
          "sectionRefs": ["station_proposals_view_s5"]
        }
      ]
    }
  ]
}
```

**Quy tắc:**
1. `type: 'tabs'` → render thành 1 khối có tiêu đề + thanh tab; mỗi phần tử `tabs[]` là 1 tab con.
2. `sectionRefs` **tham chiếu** `section.id` có sẵn trong cùng form — **không di chuyển, không nhân bản** section/field. Nhờ vậy 1 field chỉ có 1 `form_fields.config.rowId`, không trùng dữ liệu, không phải thêm mapping 1Office.
3. Tab con **không cần** `visibleWhen` riêng (tab cha đã gate). Field trong tab vẫn giữ `conditions` riêng như hiện tại.
4. **Quy tắc hiển thị (quan trọng)**: một `row` được coi là **hiển thị nếu TỒN TẠI ít nhất một nơi chứa nó đang hiển thị**. Vì cùng row `s5_r2` vừa nằm ở section "Liên kết" cấp 1 (hiện khi `LK`), vừa nằm trong tab con "Liên kết" (hiện khi `NQ_LK`) — hai trường hợp loại trừ nhau.
5. Hỗ trợ lồng nhiều cấp: `tabs[].sectionRefs` có thể trỏ tới section `type: 'tabs'` khác (dự phòng, không dùng ở 42).

### 3.4. Khả năng mở rộng N cấp (engine đệ quy — UI vẫn 2 cấp)

**Quyết định**: **engine** (render / validate / desc) viết **đệ quy không giới hạn cấp**; **FormBuilder UI** chỉ cho tạo **2 cấp**. Mục tiêu: trả giá nhỏ ngay bây giờ (~0,5 ngày) để không phải refactor 3 file engine về sau (kèm rủi ro hồi quy `stations`/`users` — R1).

**a) Schema**: một tab có thể chứa `sectionRefs` **hoặc** `tabs` (hoặc cả hai) → cấu trúc tự đệ quy, không cần đổi gì thêm.

```jsonc
{
  "type": "tabs", "id": "t1", "title": "Nhượng quyền và Liên kết",
  "visibleWhen": { "field": "mo_hinh_dau_tu", "value": "NQ_LK" },
  "tabs": [
    { "id": "t1a", "title": "Nhượng quyền", "sectionRefs": ["s6"] },
    { "id": "t1b", "title": "Liên kết", "sectionRefs": ["s5"],
      "tabs": [ /* cho phép lồng — UI chưa mở, engine đọc được */ ] }
  ]
}
```

**b) Quy ước triển khai (bắt buộc)**

| # | Quy ước | Áp ở |
|---|---|---|
| 1 | Viết **đệ quy ngay từ đầu**, không hardcode 2 cấp | `DynamicForm.renderLayoutForm`, `getApplicableFieldKeys`, `templateService.renderSection` |
| 2 | `MAX_TAB_DEPTH = 5` — chốt an toàn, vượt thì bỏ qua nhánh + log cảnh báo | cả 3 nơi |
| 3 | `visited` set khi resolve `sectionRefs` → **chặn vòng lặp** (R9) | cả 3 nơi |
| 4 | Luật: **1 section chỉ được tham chiếu bởi tối đa 1 nhánh đang hiển thị** → chặn render trùng field (R10) | FormBuilder validate + render |
| 5 | `activeTab` key theo **path** (`t1/t1a/t1a2`), không theo `id` đơn | `DynamicForm` |
| 6 | FormBuilder **chặn tạo tab trong tab con** (validate khi lưu) | `FormBuilder.handleSave` |

**c) Chi phí delta so với viết hardcode 2 cấp**

| Hạng mục | Delta |
|---|---|
| `DynamicForm` render (P3) | +1–2 giờ (1 component tự gọi lại chính nó, state theo path) |
| `getApplicableFieldKeys` (P2) | +30–45 phút (`walk()` đệ quy + `visited`) |
| `templateService` section lồng (P2) | ~0 (đệ quy là cách viết tự nhiên nhất, **ngắn hơn** hardcode 1 cấp) |
| `MAX_TAB_DEPTH` + chống vòng | +30 phút |
| Test thêm ca lồng 3 cấp (inject JSON) | +30–60 phút |
| Ghi doc | +20–30 phút |
| **Tổng** | **~3–5 giờ (≈0,5 ngày)** |

> Lưu ý: một phần delta là **âm** — viết đệ quy ngắn hơn viết 2 cấp (không phải nhân đôi markup thanh tab cấp 1 / cấp 2). Thực tế thường **+3–4 giờ**.

**d) KHÔNG bao gồm** (vẫn hoãn): UI kéo-thả N cấp trong FormBuilder (tree editor, kéo thả xuyên cấp, breadcrumb, chống vòng) — tốn thêm **3–4 ngày**.

**e) Khi nào mở rộng N cấp**: chỉ sửa `FormBuilder` (bỏ chặn ở quy ước #6, thêm UI tree) — **không cần migration**, không đụng render/validator/desc, không phải hồi quy lại 4 mô hình.

**So sánh nếu hoãn**: khi cần N cấp sẽ phải sửa **3 file engine** + hồi quy 4 mô hình + `stations`/`users` → **~1–1,5 ngày + rủi ro hồi quy cao hơn**.

#### 3.5.2. Checklist khi thêm mô hình mới (7 bước)

1. `field_definitions.options` của `mo_hinh_dau_tu` += option mới (value + label + màu).
2. `layout_config` form 13 + 14: thêm section (hoặc tab) cho mô hình mới + `visibleWhen = {field:'mo_hinh_dau_tu', value:'<NEW>'}`.
3. `form_fields`: gắn các field của mô hình mới vào row mới.
4. `desc_template_config`: thêm section mới + `condition {value:'<NEW>'}`.
5. Nếu mô hình mới cần `legal_document` bắt buộc → thêm vào `conditions` của field đó (A3).
6. Nếu mô hình mới là **Cấp 1** → sửa formula `loai_uu_tien` (A5 + bảng stations); nếu Cấp 2 → không cần.
7. Nếu value mới **có dấu `_`** → đảm bảo regex mã đề xuất đã được nới (P2 #2).

**Không cần** đụng: backend services, `validators.js`, `DynamicForm`, `templateService`, mapping 1Office (`cf14` nhận mọi giá trị).

**Với thiết kế tab (3.1 + 3.4)**: mô hình mới có tab riêng → chỉ thêm config, engine đã sẵn sàng (kể cả tab lồng).
