## 1. Bối cảnh & mục tiêu

Việc map người dùng nội bộ ↔ 1Office hiện dễ sai vì:
- 1Office có **3 loại ID** khác nhau (xem mục 3), app phải gọi API admin **lúc push** để quy đổi `ID → code`, và admin phải **nhập tay** ID → dễ lệch (đã gặp ở `NQ_HNO_0017`).
- Config API hiện tại (`1office`, id 3) đang gánh cả liên hệ lẫn danh sách nhân sự (nhét `admin_token` chung vào một chỗ).

**Mục tiêu:**
1. Tách config API thành **2 loại**: `contact` (1office liên hệ) và `personnel` (1office nhân sự), phân loại theo **Nền tảng** + **Loại API**.
2. API nhân sự **chỉ pull** danh sách nhân sự về DB hệ thống (bảng mới `external_users`).
3. Đồng bộ nhân sự: **ấn tay** + **cron** (cấu hình thời gian trên UI).
4. Liên kết hệ thống ở `/admin/users`: thay nhập ID bằng **dropdown "Mã NS - Tên"** trực quan.
5. Push/pull người dùng dùng **dữ liệu cục bộ** (không gọi API 1Office lúc push) → nhanh, ổn định, không phụ thuộc admin token khi push.

## 4. Thiết kế

### 4.1. Phân loại API

`api_configs` thêm cột `api_type`:

| `api_type` | Chức năng UI | Ghi chú |
|---|---|---|
| `contact` | Template, Mapping, Sync (push/pull/link), Test | Config hiện tại (id 3) |
| `personnel` | Sync (pull), Test | Config mới "1office nhân sự" |

UI `/admin/api-configs` bổ sung 2 trường khi tạo/sửa:
- **Nền tảng API**: `1office` (lưu vào `system_key`; sau này thêm nền tảng khác).
- **Loại API**: `Liên hệ` / `Nhân sự` (lưu `api_type`).

Tab hiển thị phụ thuộc `api_type`.

### 4.2. Database

**`api_configs`** thêm cột (idempotent, dùng `information_schema`):
```sql
ALTER TABLE api_configs
  ADD COLUMN api_type ENUM('contact','personnel') NOT NULL DEFAULT 'contact',
  ADD COLUMN sync_enabled TINYINT(1) NOT NULL DEFAULT 0,
  ADD COLUMN sync_cron VARCHAR(100) NULL,
  ADD COLUMN last_sync_at TIMESTAMP NULL,
  ADD COLUMN last_sync_status VARCHAR(30) NULL,
  ADD COLUMN last_sync_message TEXT NULL;
```

**Bảng mới `external_users`** (nhân sự 1Office lưu cục bộ):
```sql
CREATE TABLE IF NOT EXISTS external_users (
  id INT AUTO_INCREMENT PRIMARY KEY,
  api_config_id INT NULL,
  `system` VARCHAR(50) NOT NULL DEFAULT '1office',
  base_url VARCHAR(500) NULL,
  external_id VARCHAR(100) NOT NULL COMMENT 'personnel_id - ID Ho so nhan su',
  contact_id VARCHAR(100) NULL COMMENT 'ID lien he 1Office',
  code VARCHAR(100) NULL COMMENT 'Ma NS',
  fullname VARCHAR(255) NULL,
  username VARCHAR(100) NULL,
  department_id VARCHAR(100) NULL,
  department_name VARCHAR(255) NULL,
  status VARCHAR(50) NULL,
  is_active TINYINT(1) NOT NULL DEFAULT 1,
  raw_data JSON NULL,
  synced_at TIMESTAMP NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uq_system_external (system, external_id),
  KEY idx_system_code (system, code),
  KEY idx_system_contact (system, contact_id),
  KEY idx_system_active (system, is_active)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 4.3. Backend

**`personnelSyncService`** (mới):
- `syncFrom1Office(apiConfigId)`:
  1. Lấy `base_url` + admin token từ config.
  2. Gọi `/api/admin/user/gets` phân trang (`limit=100`) lấy tối đa cấu hình.
  3. **Upsert** `external_users` theo `(system, external_id)`; cập nhật `contact_id`, `code`, `fullname`, `department_*`, `status`, `raw_data`, `synced_at`, `is_active=1`.
  4. Nhân sự không còn trong danh sách → `is_active=0`.
  5. Cập nhật `api_configs.last_sync_*`.

**Scheduler cron**:
- Cài `node-cron` (`docker exec station-backend npm install node-cron` → rebuild container).
- Worker khởi động cùng app (`backend/src/workers/`), mỗi phút kiểm tra config `api_type='personnel' AND sync_enabled=1` whose `sync_cron` khớp → gọi sync (enqueue job `sync-personnel` vào `api_queue_logs` để dùng retry/log sẵn có).
- Chống trùng: 1 instance → ổn; thêm `GET_LOCK` MySQL làm chốt an toàn.

**Transformer user dùng bảng cục bộ**:
- `transformUserPush`: `user_external_map.external_id` (personnel_id) → `external_users.code`/`fullname` (không gọi API).
- `transformUserPull`: `ID` (field_raws) → `external_users.contact_id` → `personnel_id` → `findUserByExternal`.
- Bỏ phụ thuộc `getOneOfficeUserMaps` gọi API ở push/pull; `admin_token` chỉ cần khi **sync**.
- (Tùy chọn) cache in-memory ngắn cho `external_users`.

**Routes**:
- `POST /api/admin/api-configs/:id/sync-personnel` (ẩn tay, requireSuperAdmin).
- `GET /api/admin/external-users?system=1office&active=1` (mọi role quản lý user).

### 4.4. Frontend

**`AdminApiConfigPage`**:
- Form thêm "Nền tảng API" + "Loại API".
- Chọn `personnel` → chỉ hiện tab **Sync** (pull) + **Test**; ẩn Template/Mapping.
- Tab Sync: nút "Đồng bộ ngay", toggle cron, ô cron expression + preset (mỗi giờ / mỗi ngày HH:MM), hiển thị "lần sync cuối" + trạng thái.

**`UserExternalPanel`** (`/admin/users`):
- Thay ô nhập ID bằng **select** nguồn `GET /api/admin/external-users?system=1office&active=1`.
- Hiển thị `Mã NS - Họ tên (Phòng ban)`; lưu `personnel_id` vào `user_external_map`.
- Hiển thị mapping hiện có kèm tên (join bảng cục bộ).

## 10. Giao việc theo role — mode `owner_or_manager` cho trường "Người phụ trách"

**Yêu cầu:** 1Office quy trình "giao việc" chỉ nhận **1 người**, nhưng người nhận phụ thuộc role người tạo:
- Người tạo là `SALES`/`ADMIN`/`SUPER_ADMIN` → giao cho **chính người tạo**.
- Người tạo là `CTV` → giao cho **sales quản lý** (`parent_id`).

**Giải pháp:** dùng chính trường **`nguoi_phu_trach`** (id 161, đã map → `user_ids`), đổi `source_config.auto_user` sang mode mới `owner_or_manager`.

Logic:
| Role người tạo | Giá trị `nguoi_phu_trach` |
|---|---|
| SUPER_ADMIN / ADMIN / SALES | chính người tạo |
| CTV | `parent_id` (sales quản lý); nếu không có parent → chính người tạo |

**Thay đổi:**
- `dynamicUtils.applyAutoUserFields`: query `role, parent_id`; mode `owner_or_manager` xử lý theo bảng trên.
- `frontend DynamicForm.resolveAutoUserId`: thêm mode (dùng `authUser.role` + `parent_id`).
- `FieldManager`: thêm lựa chọn "Người phụ trách (CTV → Sales quản lý, còn lại → người tạo)".
- DB: field 161 `source_config = { "auto_user": "owner_or_manager" }`.
