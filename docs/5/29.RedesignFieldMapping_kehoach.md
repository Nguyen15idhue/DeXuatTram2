## 2. Hiện trạng & vấn đề

### 2.1 Bug "chọn nguồn xong bị mất"
File: `frontend/src/components/admin/FieldMappingPanel.jsx` (khối Contact Fields).

```jsx
<select value={mapping ? mapping.source_field : ''}
  onChange={(e) => { if (e.target.value && mapping) handleTargetChange(mapping, field.key); }}>
```
- `value` chỉ có khi **đã có row mapping**; field chưa link → luôn rỗng.
- `onChange` chỉ cập nhật `target_field` (chính là field.key) và **không lưu `source_field`**.
- Field chưa link: `if (e.target.value && mapping)` = false → không làm gì.
- Render lại theo `mapping.source_field` không đổi → **reset về rỗng** (cảm giác "chọn xong bị mất").

### 2.2 File upload không gắn vào contact
File: `backend/src/services/syncService.js`, `fileSyncService.js`, `oneOfficeService.js`.
- `pushTo1Office()` gọi `fileSyncService.uploadFiles()` → `oneOfficeService.uploadFilesInBatches()` → `POST /api/customer/contact/upload-file` (riêng lẻ).
- Kết quả lưu vào `request_payload.files_result` + `last_synced_data`, **không gắn vào `contactData`** → contact 1Office **không có file**.
- `processPushJob()` chỉ gửi `contactData` (không có `files`).
- Sai format: theo test thật (`test_files/1office/test_1office_api.js` Phase 5 — 11/11 PASS), file phải là **field `files` = JSON string `[{name, file: base64}]` nằm TRONG body `contact/insert` (hoặc `contact/update`)**.
- `uploadFilesInBatches` chia lô 5, `break` khi lỗi → file sau mất im lặng.
- Upload chạy lúc enqueue (route), không phải trong worker → contact lỗi vẫn để lại file mồ côi.

### 2.3 Schema chặn "1 nguồn → nhiều đích"
`api_field_mappings` có `UNIQUE (api_config_id, source_field)` → một source chỉ map được 1 target. Yêu cầu mới cho phép 1 source → nhiều target, mỗi target 1 source.
Kiểm tra data config 3: 8 mapping, target đều khác nhau → an toàn khi đổi ràng buộc.

### 2.4 Desc/File chưa được phản ánh trong UI
- `desc` thực tế do `templateService.render()` sinh ra và **luôn ghi đè** `contactData.desc`; không phải mapping 1-1.
- `files` gộp mọi field file (`legal_document`, `site_images`) về 1 target; không có row mapping.
- UI hiện không hiển thị 2 mục này như mặc định.

### 3.3 Panel phải — Contact Fields (1Office), 2 khối
**Khối "Đã link" (trên):**
- Mỗi dòng: `target ← source` + nút **X** để unlink.
- Cố định không X, không đổi:
  - `desc ← Desc Template` (label "Mô tả (Desc Template)")
  - `files ← Tất cả file đề xuất (N)` (label "Tệp đính kèm (files)")

**Khối "Chưa link" (dưới):**
- Liệt kê các field 1Office còn lại, làm vùng drop.
- Field 1Office **không hỗ trợ** → mờ + khóa, ghi chú "1Office không lưu". (Danh sách mục 3.5.)

### 3.4 Kéo–thả / lưu
- Thả source **S** lên target **T**:
  - Nếu tồn tại row `target = T`: nếu `source = S` → bỏ qua; khác → **update** row đó `source_field = S` (thay thế).
  - Chưa có → **create** row mới `(config, S, T, direction='both')`.
- Unlink: nút X → **delete** row.
- **Lưu ngay** (gọi API ngay khi drop/unlink), rollback UI nếu lỗi.
- **Tự động publish**: mapping mới dùng ngay, `sync_enabled = 1` luôn; không còn toggle bật/tắt.

### 3.5 Field 1Office không hỗ trợ (khóa drop)
Theo docs/5/27: `gender`, `group_type_id`, `trade_ids`, `websites`, `status_id`, `source_id`, `region` (và mảng `contacts`, `detail` — API không parse).

### 3.6 Hướng đồng bộ: UI thiên Push, nhưng GIỮ Pull
- Panel này **thiên về Push** (đẩy đề xuất → 1Office): **không hiển thị** lựa chọn direction.
- Nhưng để **Push + Pull + Link đều hoạt động**, mapping thường giữ `direction = 'both'` (mặc định); các mapping hệ thống tự sinh (`code`) giữ `push`.
- **Không ép** toàn bộ mapping sang `push` (nếu ép, `processPull` lọc `pull|both` sẽ rỗng → Pull hỏng).
- Không đụng tới `syncService.processPull`, `linkProposal`, `unlinkProposal` → Pull và Link giữ nguyên.

### 3.7 Bảo toàn 3 luồng Push / Pull / Link (bắt buộc)
Kế hoạch 29 **không được làm hỏng** 3 chức năng ở `/admin/proposals`:

| Luồng | Cơ chế | Tác động kế hoạch 29 |
|-------|--------|----------------------|
| **Push** (Đẩy sang 1Office) | `syncService.pushTo1Office` → queue → `processPushJob` lọc `sync_enabled && direction in (push,both)` | Vẫn chạy; bổ sung desc + files. Không đổi điều kiện lọc. |
| **Pull** (Lấy về từ 1Office) | `syncService.processPull` lọc `sync_enabled && direction in (pull,both)` | **Giữ nguyên**. Vì không ép direction='push', mapping `both` cũ vẫn được pull. |
| **Link / Unlink** | `syncService.linkProposal` / `unlinkProposal` (chỉ set `contact_1office_code/id` + refresh `id_1office`) | **Không đụng** — độc lập với bảng mapping. |

Nguyên tắc bắt buộc:
1. Không `UPDATE` `sync_enabled`/`direction` của row cũ khi migrate.
2. Mapping mới mặc định `direction='both'`, `sync_enabled=1`.
3. Không sửa logic `processPull`, `linkProposal`, `unlinkProposal`.
4. Việc ẩn dropdown direction chỉ là UI; giá trị `direction` trong DB giữ nguyên.

## 4. Thiết kế dữ liệu

### 4.1 Script SQL mới `database/44-alter-field-mappings-target-unique.sql`
```sql
-- Bỏ unique theo source (để 1 nguồn -> nhiều đích)
SET @idx := (SELECT COUNT(*) FROM INFORMATION_SCHEMA.STATISTICS
  WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME='api_field_mappings'
    AND INDEX_NAME='uq_field_mappings_config_source');
SET @drop := IF(@idx > 0, 'ALTER TABLE api_field_mappings DROP INDEX uq_field_mappings_config_source', 'SELECT 1');
PREPARE s1 FROM @drop; EXECUTE s1; DEALLOCATE PREPARE s1;

-- Thêm unique theo target (1 đích <- 1 nguồn)
SET @idx2 := (SELECT COUNT(*) FROM INFORMATION_SCHEMA.STATISTICS
  WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME='api_field_mappings'
    AND INDEX_NAME='uq_field_mappings_config_target');
SET @add := IF(@idx2 = 0, 'ALTER TABLE api_field_mappings ADD UNIQUE KEY uq_field_mappings_config_target (api_config_id, target_field)', 'SELECT 1');
PREPARE s2 FROM @add; EXECUTE s2; DEALLOCATE PREPARE s2;
```
> Lưu ý: xử lý trùng target nếu có trước khi add unique (config 3 hiện không trùng).
> **KHÔNG** đụng tới `sync_enabled` / `direction` của các row cũ (giữ nguyên để Push/Pull không đổi hành vi). Chỉ mapping **tạo mới** mới đặt `sync_enabled=1`, `direction='both'`.

### 4.2 `desc` và `files` KHÔNG lưu vào bảng mapping
- Là **hằng số đặc biệt** trong backend + UI.
- Nếu data cũ có row `target_field IN ('desc','files')` → xóa khi chạy script (hoặc bỏ qua ở UI). Đề xuất xóa row `description → desc` (vì desc do template sinh, không dùng source).

### 5.3 `syncService.pushTo1Office` + worker

### 5.4 `oneOfficeService`

### 5.5 `fileSyncService`

## 7. Xử lý file >5 (điểm rủi ro cao — cần test thật)

Test cũ: 1 request `contact/insert` với 5 file (~17.5MB) PASS. **Chưa test >5 file và chưa rõ `update` có append file không.**

Phương án đề xuất theo thứ tự ưu tiên:
1. **Thử gửi tất cả file trong 1 request** (nếu API không giới hạn cứng) — cần spike test 6–10 file.
2. Nếu có giới hạn N (giả định 5):
   - `insert` với N file đầu.
   - `update` với từng lô N file tiếp theo.
   - **Bắt buộc verify `update` append** (test thật). Nếu replace → phải gửi lại toàn bộ file ở mỗi lần update, hoặc gộp.
3. Fallback: nếu API không nhận nhiều lô → lưu danh sách link file vào `desc` (không lý tưởng).

> Trước khi code phần này, chạy spike test với 1Office thật (có thể tạo contact test) để chốt hành vi.

## 10. Edge cases & rủi ro

1. **1Office update có append file?** — rủi ro lớn nhất, chưa có bằng chứng. Cần spike (B1).
2. **Giới hạn số file/dung lượng mỗi request** — chưa rõ.
3. **File lớn (10MB) × nhiều file** → payload lớn, timeout; cần giới hạn và retry.
4. **Trùng target khi migrate** — phải kiểm tra trước khi add unique.
5. **Mapping trỏ source không tồn tại** (`mo_hinh` vs `mo_hinh_dau_tu`, `owner_email`...) — data hygiene cũ, nên rà lại.
6. **Direction `pull` cho field không pull được** (files/desc) — ép `push`.
7. **File mồ côi** — nếu chuyển upload vào worker và push lỗi, file có thể vẫn được gửi 1 phần; cần đảm bảo gửi cùng lúc với contact.
