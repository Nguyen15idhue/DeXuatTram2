## Mô hình role

| Role | Đăng nhập | Admin panel | Phạm vi |
|---|---|---|---|
| `SUPER_ADMIN` | ✓ | Full mọi thứ (tạo super admin + tất cả trang cấu hình) | Toàn hệ thống |
| `ADMIN` | ✓ | Full **trừ** (1) tạo super admin + (2) truy cập trang cấu hình: `/admin/fields`, `/admin/forms`, `/admin/views`, `/admin/data-lists`, `/admin/map-config`, `/admin/roles` (phân quyền mới) | Toàn hệ thống |
| `SALES` | ✓ | Giới hạn: users (CTV mình), stations (xem), proposals (nhánh mình), dashboard (nhánh mình) | Nhánh mình |
| `CTV` | ✓ | Không (= `USER` hiện tại) | Bản thân |
| `GUEST` | Không | Không | File 19, không đổi |

**DB `users` thêm**: `parent_id` (self-FK, NULL với super/admin; CTV trỏ sales), `external_id` (nullable + unique, để map hệ thống khác sau này), `role` mở enum 5 giá trị. Dữ liệu cũ: `USER` → `CTV` (giữ nguyên id/quyền thực tế), admin hiện tại → `SUPER_ADMIN`.

**Quy tắc nhánh sales**: scope sales = `user_id IN (sales + toàn bộ CTV con trực tiếp)`. Đề xuất của CTV thuộc nhánh sales đó (user_id vẫn là CTV, nhưng sales thấy trong nhánh mình). Admin/super thấy proposal và biết CTV thuộc sales nào — hiển thị 2 cột riêng `CTV` + `Sales quản lý` thay vì if/else phức tạp.

## Phase 1 — DB roles + middleware phân quyền

### Chi tiết bước thực hiện

#### Bước 1.1: SQL thủ công (không DROP, không migration tool)

**File**: `database/27-add-rbac-fields.sql` (tên đề xuất, chạy thủ công)

- `ALTER TABLE users MODIFY role ENUM('SUPER_ADMIN','ADMIN','SALES','CTV')` — kiểm tra enum hiện tại trước khi sửa.
- `ADD COLUMN parent_id INT NULL` + self-FK (`ON DELETE SET NULL`), `ADD COLUMN external_id VARCHAR(100) NULL UNIQUE`.
- Data: `UPDATE users SET role='CTV' WHERE role='USER'`; `UPDATE users SET role='SUPER_ADMIN' WHERE email='<admin-hiện-tại>'` (user duyệt email cụ thể).

## Phase 2 — `/admin/users`: cây phân cấp + tạo user theo quyền

### Chi tiết bước thực hiện

#### Bước 2.1: API users theo scope

- **Query tree**: dùng recursive CTE (`WITH RECURSIVE`) để lấy toàn bộ nhánh con của 1 sales trong 1 query (MySQL 8.0 hỗ trợ). Sales query → `WHERE parent_id = me OR id = me`; admin/super → lấy all, build tree trong JS bằng `parent_id` map.
- List trả cây (Super → Admin → Sales → CTV) thay vì table phẳng: super/admin thấy toàn cây; sales chỉ thấy nhánh mình (mình + CTV con).
- **Create**: validate role được phép theo người tạo:
  - Sales: chỉ tạo `CTV`, server tự gán `parent_id` = mình, bỏ qua `parent_id` client gửi.
  - Admin: tạo `CTV`, `SALES`, `ADMIN` — không tạo được `SUPER_ADMIN`.
  - Super: tạo tất cả role.
  - Validate: `email` unique + đúng format, `password` >= 8 ký tự, `external_id` unique (nếu có).
- **Update**: chỉ trong phạm vi quản lý (sales không sờ ngoài nhánh; không tự thay đổi role mình lên cao hơn); `external_id` unique khi sửa.
- **Delete**: sales xóa CTV mình → `parent_id` của CTV đó (nếu có proposals) giữ lại, orphan về sales; admin/super xóa tự do.

#### Bước 2.2: UI tree + form tạo/sửa (dùng lại DynamicTable + view đã cấu hình)

- **Table dùng view Users (view 7)**: không tự vẽ table riêng — dùng `DynamicTable` với đúng columns/width/sort/filter đã cấu hình; dữ liệu truyền vào đã sắp xếp theo cây; indent cấp bậc qua prop `rowDepth` mới của DynamicTable (generic, bọc ô đầu bằng padding theo depth, không ảnh hưởng các trang khác).
- **Màu badge role**: cấu hình trong options của field role (SUPER đỏ/ADMIN tím/SALES xanh/CTV xám) — FieldRenderer render sẵn, không code màu cứng.
- **Cột mã ngoài**: field `external_id` (fixed) + thêm vào view 7 (database/29).
- **Tree component**: sắp xếp theo cây (super → admin → sales → CTV, theo tên trong cùng cấp); node hiện đúng columns của view.
- **Action buttons theo level**:
  - Super: sửa/xóa mọi node, tạo mọi role.
  - Admin: sửa/xóa sales + CTV (trừ super); tạo CTV/sales/admin.
  - Sales: sửa/xóa CTV mình; tạo CTV.
- **Search**: lọc theo tên/email trong nhánh được phép, gồm cả cha của kết quả (không hiển thị kết quả ngoài nhánh).
- **Phân trang**: bỏ phân trang server ở trang này (cây + sort/filter client của DynamicTable xung đột phân trang); user ít nên load `all=1`.
- **Form tạo user**: ẩn/hiện role options theo quyền người tạo (`optionAllowlist` mới ở DynamicForm/DynamicField); ô mật khẩu **để trống mặc định** (bỏ pre-fill 123456; submit rỗng vẫn mặc định 123456 phía payload).
- **Hiển thị `external_id`**: cột của view 7, để trống chờ map hệ thống khác.

#### Bước 2.3: Field type `password` (chốt với user 06/09/2026)

- **Ý tưởng user**: thêm type `password` trong `/admin/fields`; field này liên kết thẳng cột gốc (`source_type=fixed` + `key=password` — đúng cơ chế fixed sẵn có, không cần UI liên kết riêng); giá trị nhập vào hash rồi mới lưu, không qua `custom_data`.
- **Backend**: `allowedTypes` thêm `password`; engine hard-code 2 luật — đọc luôn blank/strip (API record/list/export không bao giờ trả hash hay giá trị thật), ghi thì bcrypt hash khi non-empty và skip khi rỗng; cấm reference trong formula, cấm search/filter/sort theo password; import bỏ qua cột password.
- **Frontend**: DynamicField case `password` (input masked, edit luôn rỗng + placeholder "Để trống = giữ nguyên"); FieldRenderer hiện `********` cố định (không theo độ dài — tránh lộ độ dài mật khẩu); FormBuilder/ViewBuilder cho chọn type.
- **Tích hợp**: form Users (form 8) kéo field password vào thay ô cứng ở modal tạo (xóa ô cứng); modal Đổi MK + endpoint `PATCH /:id/password` giữ nguyên.
- **Lưu ý bảo mật**: hash chỉ bảo vệ lúc lưu trữ + response; đường truyền browser → backend vẫn là plaintext nên prod bắt buộc HTTPS.

## Cross-cutting — Error handling + Swagger (áp dụng toàn bộ 25)

### Frontend error handling

- **403 từ API**: toast "Bạn không có quyền thực hiện thao tác này" + redirect phù hợp (về trang chủ nếu vào `/admin/*` trái phép; về danh sách nếu thao tác cụ thể bị chặn).
- **401 từ API** (token hết hạn): redirect `/login` + toast "Phiên đăng nhập đã hết hạn".
- **Loading states**: tree users, dashboard stats hiện skeleton/spinner khi load.
- ** optimistic update**: sau create/update/delete user, cập nhật tree ngay (không cần reload trang).

### Backend error handling

- **403 trả về**: `{ success: false, message: "Không có quyền truy cập tài nguyên này" }` — không lộ chi tiết resource không tồn tại (tránh enumeration attack).
- **Validation error 400**: `{ success: false, message: "...", errors: [{field, message}] }` — đúng format hiện tại.

### Swagger

- Mỗi endpoint mới/đổi phải có `@swagger` JSDoc: `tags`, `summary`, `security: [{ bearerAuth: [] }]`, `responses` (200, 400, 403, 404, 500).
- Swagger UI tại `/api-docs` — kiểm tra sau mỗi phase.
