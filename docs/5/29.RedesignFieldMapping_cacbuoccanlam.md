## Phase 0 — Chuẩn bị + spike test 1Office

### Mục tiêu
Xác định chính xác hành vi API 1Office với file: gửi bao nhiêu file/request, `contact/update` có append file không, giới hạn dung lượng.

### Các bước
1. Đọc lại kết quả test cũ: `test_files/1office/test_1office_api.js` (Phase 5) + `test_files/1office/TEST_PLAN.md`.
2. Viết script test tạm (trong `test_files/1office/`) gọi thật `POST /api/customer/contact/insert` với `files = JSON.stringify([{name, file}])`.
   - Test N = 6, 8, 10 file.
   - Sau insert, gọi `contact/item?code=...` kiểm tra `num_file` / danh sách file.
3. Test update: insert 2 file → gọi `contact/update` thêm 3 file → kiểm tra tổng file = 5 (append) hay = 3 (replace).
4. Ghi lại giới hạn (số file, tổng dung lượng) và lỗi trả về.

### Yêu cầu cần đạt
- Biết chắc **số file tối đa / 1 request** (hoặc xác nhận không giới hạn thực tế).
- Biết `update` **append hay replace** file.
- Có kết luận để chọn chiến lược mục 7 kế hoạch.

### Checklist test
- [ ] Insert 6 file → thành công, contact có đủ 6 file.
- [ ] Insert 10 file → kết quả rõ ràng (thành công hoặc lỗi cụ thể).
- [ ] Update thêm file → biết append/replace.
- [ ] Ghi lại response mẫu vào `docs/5/29..._ketquadadat.md`.

### Ghi chú
- Test này **tạo contact thật trên 1Office** → cần user cho phép; dùng code có prefix `TEST_` để dễ dọn.
- Nếu sandbox/container không ra được Internet tới 1Office thì ghi chú lại và chuyển sang test thủ công.

## Phase 1 — DB migration (script 44)

### Mục tiêu
Cho phép 1 nguồn → nhiều đích, mỗi đích 1 nguồn; không đụng dữ liệu cũ.

### Các bước
1. Tạo `database/44-alter-field-mappings-target-unique.sql`:
   - Drop `uq_field_mappings_config_source` (nếu tồn tại).
   - Add `uq_field_mappings_config_target (api_config_id, target_field)` (nếu chưa có).
   - Không UPDATE `sync_enabled`/`direction`.
2. Kiểm tra trùng target trước khi add unique (config 3 hiện không trùng).
3. Backup DB trước khi chạy.
4. Chạy script trên DB hiện tại; verify index.

### Yêu cầu cần đạt
- Index `uq_field_mappings_config_source` không còn.
- Index `uq_field_mappings_config_target` tồn tại.
- Dữ liệu mapping cũ **không đổi** (đếm trước/sau bằng nhau).

### Checklist test
- [ ] `SHOW INDEX FROM api_field_mappings` thấy `uq_field_mappings_config_target`, không thấy `uq_field_mappings_config_source`.
- [ ] `SELECT COUNT(*)` mapping config 3 trước/sau = 8.
- [ ] `direction`/`sync_enabled` của 8 row giữ nguyên.
- [ ] Chạy lại script lần 2 → không lỗi (idempotent).

### Ghi chú
- Idempotent bằng `INFORMATION_SCHEMA.STATISTICS` + `PREPARE/EXECUTE`.
- Nếu có config khác trùng target → xử lý thủ công trước khi add unique.

## Phase 2 — Backend: mapping service/controller + unsupported list

### Mục tiêu
API mapping hỗ trợ target-unique, trả về thông tin field đặc biệt/không hỗ trợ cho UI.

### Các bước
1. `fieldMappingService.js`:
   - `create`: bỏ check trùng `source_field`; thêm check trùng `target_field` (cùng config).
   - `update`: đổi `target_field` phải check trùng target khác id; **không đổi `direction`**.
   - Thêm `getByTarget(configId, target)`.
2. `fieldMappingController.getFieldTypes`:
   - Trả `unsupported: true` cho: `gender, group_type_id, trade_ids, websites, status_id, source_id, region` (và `contacts`, `detail`).
   - Trả 2 field đặc biệt `desc`, `files` với `special: true`.
   - Đảm bảo `files` có mặt (type `json`, label "Tệp đính kèm").
3. `fieldMapper.js`: tách danh sách field 1Office không hỗ trợ dùng chung.
4. Giữ nguyên Swagger, cập nhật mô tả nếu cần.

### Yêu cầu cần đạt
- Tạo được 2 mapping cùng `source_field` (khác target) không lỗi.
- Tạo/đổi mapping trùng `target_field` bị chặn (400).
- `getTypes` có cờ `unsupported` + 2 field `special`.

### Checklist test
- [ ] `POST` mapping (source=A, target=name) OK.
- [ ] `POST` mapping (source=A, target=phones) OK (nguồn lặp).
- [ ] `POST` mapping (source=B, target=name) → 400 (target trùng).
- [ ] `PUT` đổi target sang target đã có → 400.
- [ ] `GET /types` chứa `files`, `desc` (special) và `unsupported` đúng danh sách.

### Ghi chú
- Không sửa `processPull`/`linkProposal`/`unlinkProposal`.
- `direction` giữ nguyên khi update.

## Phase 3 — Backend: sync/worker gom desc + files, xử lý >5 file

### Mục tiêu
1 contact 1Office nhận đủ desc + tất cả file khi push.

### Các bước
1. `fileSyncService.js`: thêm `buildFilesPayload(files)` → `[{name, file: base64}]`.
2. `syncService.pushTo1Office`: **bỏ** upload file riêng ở route.
3. `workers/queueWorker.js` (`processPushJob`):
   - Build `contactData` gồm mapping thường + `desc` (template) + `files` (payload).
   - Gọi `insertContact`/`updateContact` kèm `files`.
   - Nếu >N file (theo Phase 0): insert N file đầu rồi `update` các lô tiếp.
4. `oneOfficeService`: không gọi `uploadFile`/`uploadFilesInBatches` trong luồng push.
5. Ghi snapshot `last_synced_data` (files thực tế đã gửi).

### Yêu cầu cần đạt
- Contact 1Office sau push có `desc` + đúng số file của proposal.
- >5 file (theo ngưỡng Phase 0) vẫn đẩy đủ.
- Push thất bại → không để file mồ côi (gửi cùng contact).

### Checklist test
- [ ] Proposal 0 file → contact có desc, không có files.
- [ ] Proposal 1 file → contact có 1 file.
- [ ] Proposal 5 file → contact có 5 file.
- [ ] Proposal 6/10 file → contact đủ file (theo chiến lược Phase 0).
- [ ] `desc` render đúng HTML + field custom.
- [ ] Push lỗi mạng → job failed, retry hoạt động, không tạo contact rác.

### Ghi chú
- Payload base64 lớn → theo dõi timeout; có thể cần giới hạn.
- Thứ tự ưu tiên chiến lược: gửi 1 request nếu được → nếu không, batch insert/update.

## Phase 4 — Frontend: redesign FieldMappingPanel

### Mục tiêu
Panel kéo–thả: trái chỉ hiển thị + kéo; phải 2 khối linked/unlinked; desc/files cố định; lưu ngay.

### Các bước
1. **Trái — Proposal Fields**:
   - Bỏ toggle/X/+Thêm; giữ icon (i) + ghi chú Desc.
   - `draggable`; badge `^N` = số mapping có `source_field` = field.
   - Giữ nút Get + lưu `selected_fields`.
2. **Phải — Contact Fields**:
   - Khối "Đã link": mappings + 2 dòng đặc biệt `desc`, `files` (không X).
   - Khối "Chưa link": target còn lại, drop zone; field `unsupported` mờ + khóa.
3. Drop handler: upsert ngay (create/update/delete), optimistic + rollback.
4. Sửa bug select cũ (đã bỏ select, thay bằng kéo–thả).
5. `services/api.js`: nếu cần thêm helper (không bắt buộc).

### Yêu cầu cần đạt
- Kéo field trái → target phải ⇒ hiện ở "Đã link", biến khỏi "Chưa link", lưu server ngay.
- Thả source khác vào target đã link ⇒ thay thế.
- X ⇒ unlink, lưu server ngay.
- Badge `^N` đúng.
- `unsupported` không thả được.

### Checklist test (Playwright)
- [ ] Kéo 1 field → xuất hiện khối "Đã link"; reload vẫn còn.
- [ ] Badge `^N` tăng khi kéo cùng source sang target 2.
- [ ] Thả source khác vào target đã link → thay thế, không nhân đôi.
- [ ] X → unlink, reload không còn.
- [ ] Field unsupported: mờ + không drop được.
- [ ] `desc`, `files` luôn ở "Đã link", không có X.
- [ ] Không có lỗi console.

### Ghi chú
- Giữ `used_in_desc` warning + nút Get.
- DnD có thể dùng HTML5 native hoặc thư viện sẵn có.
