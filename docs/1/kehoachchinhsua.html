0. LƯU Ý QUAN TRỌNG

stations chỉ là ví dụ, không phải đối tượng duy nhất sử dụng Dynamic Field.

Kiến trúc Dynamic phải được xây dựng ở mức tầng dùng chung của hệ thống. Không được hard-code logic Dynamic riêng cho bảng stations.

Các bảng nghiệp vụ thực tế có thể áp dụng Dynamic Field, ví dụ:

users stations station_proposals customers contracts projects documents

Hệ thống phải xác định Dynamic Field dựa trên entity/table, thay vì viết riêng logic cho từng bảng.

Ví dụ

field_definitions

entity              key                 label
---------------------------------------------------------
users               employee_code       Mã nhân viên
users               department          Phòng ban
users               avatar              Ảnh đại diện

stations            antenna_height      Chiều cao anten
stations            tower_type          Loại cột

station_proposals   land_type           Loại mặt bằng
station_proposals   investment_cost     Chi phí đầu tư
station_proposals   legal_document      Hồ sơ pháp lý

Như vậy cùng một cơ chế Dynamic có thể phục vụ nhiều bảng.

Không được thiết kế theo kiểu: station_dynamic_fields, station_forms, station_views nếu không có lý do nghiệp vụ đặc biệt.

Nên thiết kế thành các bảng cấu hình dùng chung, có trường xác định entity.

2. PHẠM VI DYNAMIC

Không phải tất cả field đều phải Dynamic. Mỗi bảng nghiệp vụ được chia thành: 

Business Table
│
├── Fixed Fields
│   ├── id
│   ├── code
│   ├── name
│   ├── status
│   └── created_at
│
└── Dynamic Fields
    ├── custom_data JSON
    ├── được định nghĩa bởi field_definitions
    └── có thể thay đổi runtime

Dynamic phù hợp với các thông tin có khả năng thay đổi, bổ sung theo yêu cầu nghiệp vụ hoặc cần cấu hình từ Admin.

4. FIELD DEFINITION

Tạo bảng dùng chung: field_definitions.

Bảng này lưu định nghĩa của Field, không lưu giá trị thực tế của từng record.

Field Ý nghĩa
id ID của field
entity Field thuộc entity/bảng nghiệp vụ nào
key Tên kỹ thuật ổn định
label Tên hiển thị
type Loại field
source_type column hoặc json
required Bắt buộc nhập
validation Quy tắc validate
options Danh sách option của select
formula Công thức nếu là Formula Field
status Active/Inactive

Ví dụ

id | entity            | key              | label             | type
----------------------------------------------------------------------
1  | stations          | antenna_height   | Chiều cao anten   | number
2  | stations          | tower_type       | Loại cột          | select
3  | users             | employee_code    | Mã nhân viên      | text
4  | station_proposals | land_type        | Loại mặt bằng     | select
5  | station_proposals | legal_document   | Hồ sơ pháp lý     | file

5. FIXED FIELD & DYNAMIC FIELD

Fixed Field

Field quan trọng, ổn định, thường xuyên được query, filter hoặc join nên để thành column thật trong MySQL. 

stations.code
stations.name
stations.status
stations.latitude
stations.longitude

Dynamic Field

Field có thể thêm/xóa/đổi cấu hình bởi Admin, không cần thay đổi schema database. 

stations.custom_data

{
    "antenna_height": 35.5,
    "tower_type": "self_support"
}
Không ALTER TABLE khi Admin tạo Dynamic Field.

6. CÁC LOẠI FIELD

Phiên bản đầu có thể hỗ trợ:

text textarea number email phone url date datetime boolean select multiselect file formula

Mỗi field type nên có:

  • Input/Editor
  • Renderer
  • Validation
  • Serialization

7. FORM BUILDER

Form Builder không tạo Field mới. Nó lấy Field từ field_definitions và cho Admin kéo-thả vào Form. 

field_definitions
       │
       ▼
   Form Builder
       │
       ├── kéo field
       ├── sắp xếp
       ├── cấu hình hiển thị
       └── lưu
       │
       ▼
form_fields

Cấu trúc

forms
├── id
├── entity
├── name
└── status

form_fields
├── id
├── form_id
├── field_id
├── order
├── visible
└── config

Ví dụ: 

Form: Tạo đề xuất trạm

1. Mã đề xuất
2. Tên vị trí
3. Loại mặt bằng
4. Chi phí đầu tư
5. Hồ sơ pháp lý

Các Field này đều lấy từ kho field_definitions.

9. ẨN / HIỆN FIELD

Visibility phải được cấu hình riêng theo ngữ cảnh. 

Field
 │
 ├── Form visibility
 │
 ├── Table visibility
 │
 └── Dashboard visibility

Ví dụ: 

Field: Chi phí đầu tư

Form       → Hiện
Table      → Hiện
Dashboard  → Ẩn
Ẩn field trên frontend không phải là cơ chế bảo mật. Permission và authorization bắt buộc phải được kiểm tra ở backend.

10. NHẬP DỮ LIỆU

Frontend gửi dữ liệu theo key của Field. 

{
    "code": "HN001",
    "name": "Trạm Hà Nội",
    "status": "active",

    "antenna_height": 35.5,
    "tower_type": "self_support"
}

Backend dựa vào field_definitions để xác định field nào là fixed và field nào là dynamic. 

code
→ stations.code

name
→ stations.name

status
→ stations.status

antenna_height
→ stations.custom_data.antenna_height

tower_type
→ stations.custom_data.tower_type

11. FORMULA FIELD

Formula cũng được quản lý trong field_definitions.

Ví dụ:

quantity
unit_price
total

Formula:
quantity * unit_price

Frontend có thể tính realtime để hiển thị. Backend phải tính hoặc kiểm tra lại khi lưu.

Không tin giá trị Formula do frontend gửi lên.

13. BẢNG FILES

Không lưu binary file trực tiếp trong MySQL. Tạo bảng metadata: files. 

files
├── id
├── original_name
├── storage_key
├── mime_type
├── size
├── checksum
├── storage_provider
├── uploaded_by
├── status
└── created_at

Ví dụ: 

id:              f001
original_name:   giay_phep.pdf
storage_key:     station_proposals/123/f001.pdf
mime_type:       application/pdf
size:            2457600

14. CUSTOM_DATA & FILE

custom_data chỉ lưu reference đến file, không lưu binary. 

{
    "license": {
        "file_id": "f001"
    }
}

Multiple file: 

{
    "site_images": [
        "f001",
        "f002",
        "f003"
    ]
}

Quan hệ: 

business_table.custom_data
          │
          │ file_id
          ▼
        files
          │
          │ storage_key
          ▼
     File Storage

15. FILE STORAGE

Ở giai đoạn development và hệ thống một server, sử dụng persistent storage trên host. 

Project
│
├── backend/
├── frontend/
├── storage/
│   └── uploads/
└── docker-compose.yml

File thật nằm trong: 

storage/uploads/

Database chỉ lưu: 

storage_key

Sau này có thể chuyển File Storage sang S3-compatible storage mà không phải thay đổi cấu trúc custom_data.

16. KHÔNG LƯU FILE CHỈ TRONG DOCKER CONTAINER

Không lưu file upload vào filesystem của container nếu không có persistent volume/bind mount. 
Windows Host

./storage/uploads
        │
        │ Docker Bind Mount
        ▼
Container

/app/uploads

Container chứa chương trình. Host storage chứa dữ liệu lâu dài.

18. FILE CONFIGURATION

File Field cần có cấu hình. 

{
    "type": "file",
    "multiple": true,
    "max_files": 5,
    "max_size": 10485760,
    "allowed_extensions": [
        ".pdf",
        ".jpg",
        ".png"
    ]
}

Có thể hỗ trợ:

  • Cho phép một hoặc nhiều file
  • Số lượng file tối đa
  • Dung lượng tối đa
  • Extension cho phép
  • MIME type cho phép
Backend phải validate lại file. Không chỉ kiểm tra ở frontend.

19. DOWNLOAD FILE

Không nên public trực tiếp toàn bộ thư mục upload. 

GET /api/files/:id/download

Backend thực hiện: 

Authentication
      ↓
Authorization
      ↓
Kiểm tra quyền truy cập file
      ↓
Tìm metadata trong files
      ↓
Download / tạo temporary URL

Không cho phép user chỉ cần biết file ID là có thể truy cập file của người khác.

20. QUERY & PAGINATION

Bảng quản lý nên sử dụng pagination. 

GET /api/stations?page=1&limit=10

GET /api/station-proposals?page=1&limit=10

GET /api/users?page=1&limit=10

Không query toàn bộ dữ liệu nếu frontend chỉ hiển thị 10 record.

Dynamic data nên được lấy cùng request, không gọi API riêng cho từng field. 

1 API Request
       ↓
10 Records
       ↓
custom_data của 10 Records
       ↓
Frontend render Dynamic Fields

21. PERFORMANCE & INDEX

Với khoảng 10 record/trang và khoảng 10 Dynamic Field trên mỗi record, custom_data JSON thường đủ nhanh cho giai đoạn đầu.

Không tạo index cho tất cả Dynamic Field.

Field nào thường xuyên:

  • Search
  • Filter
  • Sort

mới cân nhắc tối ưu bằng:

  • Generated Column
  • Functional Index
  • Hoặc chuyển thành Fixed Column nếu thực sự trở thành dữ liệu cốt lõi
Không nên tạo hàng trăm index chỉ vì Dynamic Field có thể được tìm kiếm.

22. CACHE / REDIS

Không sử dụng Redis ở phiên bản hiện tại.

Kiến trúc ban đầu: 

React
  ↓
Node.js
  ↓
MySQL

Nếu cần cache sau này có thể sử dụng memory cache trong Node.js cho các cấu hình như:

  • field_definitions
  • form configuration
  • view configuration
  • select options

Redis chỉ được cân nhắc khi hệ thống thực sự có nhu cầu distributed cache, nhiều backend instance hoặc các chức năng cần shared state.

23. RUNTIME CONFIGURATION — KHÔNG RESTART

Đây là yêu cầu quan trọng của toàn bộ kiến trúc.

Khi Admin thêm Dynamic Field: 

Admin
  ↓
Tạo Field
  ↓
INSERT field_definitions
  ↓
Form/Table Builder đọc config mới
  ↓
Frontend hiển thị Field mới

Không được yêu cầu: 

❌ Restart Node.js
❌ Restart Docker
❌ Rebuild Frontend
❌ ALTER TABLE
❌ Database Migration

Khi Admin thay đổi cấu hình Form hoặc Table, cấu hình mới phải có hiệu lực ngay với request tiếp theo.

Nếu sau này có cache: 

Update Configuration
        ↓
Update MySQL
        ↓
Invalidate Cache
        ↓
Request tiếp theo
        ↓
Đọc Configuration mới

25. NGUYÊN TẮC CODEBASE

ARCHITECTURE RULES

1. Use MySQL as the primary database.

2. Do NOT use Redis.

3. Dynamic architecture MUST be reusable across
   multiple business entities/tables.

4. stations is only an example entity.

5. users, stations, station_proposals and other
   business tables may use Dynamic Fields.

6. Fixed business fields are physical database columns.

7. Dynamic fields MUST be stored in custom_data JSON.

8. Creating a Dynamic Field MUST NOT modify
   the business table schema.

9. field_definitions stores field metadata,
   not record values.

10. field_definitions MUST contain the target entity.

11. field.key is the stable machine identifier.

12. field.label is the display label.

13. Forms reference field_definitions.

14. Tables/Views reference field_definitions.

15. Form Builder MUST NOT create duplicate field definitions.

16. Table Builder controls table display configuration.

17. Frontend visibility is NOT a security mechanism.

18. Backend MUST enforce authorization.

19. Formula values MUST be validated/recalculated
    on the backend.

20. File fields store file references,
    not binary data.

21. File metadata belongs in the files table.

22. Actual files belong in persistent storage.

23. Docker containers MUST NOT be the only storage
    location for uploaded files.

24. Development storage:
    ./storage/uploads:/app/uploads

25. API list endpoints MUST use pagination.

26. Do NOT make one API request per Dynamic Field.

27. Do NOT create indexes for every Dynamic Field.

28. Index only fields that actually require
    search/filter/sort optimization.

29. Dynamic configuration MUST work at runtime.

30. Adding/modifying Dynamic Fields, Forms and Views
    MUST NOT require restarting Node.js.

31. Configuration cache, if introduced later,
    MUST be invalidated after configuration changes.

32. Keep the architecture simple.

33. Do not introduce Redis, Elasticsearch, queues
    or other infrastructure unless there is
    a demonstrated technical requirement.

Kết luận kiến trúc

Business Table giữ dữ liệu cố định → custom_data JSON giữ dữ liệu Dynamic → field_definitions định nghĩa Dynamic Field → Form/Table Builder tham chiếu Field → files quản lý metadata → Persistent Storage lưu file thật.

Mục tiêu cuối cùng là Admin có thể thêm Field, kéo Field vào Form hoặc Table, thay đổi thứ tự, ẩn/hiện, cấu hình validation và upload file mà không phải sửa code nghiệp vụ và không phải restart hệ thống.
